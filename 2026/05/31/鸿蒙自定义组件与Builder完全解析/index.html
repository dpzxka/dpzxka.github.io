鸿蒙自定义组件与 @Builder 完全解析：从组件基础到插槽模式

发表于2026-05-31|更新于2026-05-31|harmonyos
|总字数:6k|阅读时长:24分钟|浏览量:

在构建一个复杂的鸿蒙应用时，自定义组件是不可避免的。重复的 UI 结构需要抽象、公共的业务逻辑需要封装、复杂的页面需要拆解——这一切都指向同一个答案：自定义组件。

ArkUI V2 基于 @ComponentV2 装饰器提供了一套全新的自定义组件体系。相比 V1 的 @Component，V2 在状态管理、构建函数、插槽复用等方面做了大幅改进。

本文将从最基础的自定义组件写法入手，逐步深入到 @Builder、@BuilderParam、@Track、@Reusable 等核心特性，最后用一个完整的表单组件实战来串联所有知识点。

一、@ComponentV2：新一代自定义组件

V2 的自定义组件使用 @ComponentV2 装饰器，配合 struct 声明和一个 build() 方法来完成 UI 描述。

1.1 基本结构

先看一个最简单的自定义组件：

这里有三个关键点：

第一，@ComponentV2 而不是 @Component。V2 的自定义组件装饰器从 @Component 变成了 @ComponentV2。这是最直观的变化，但背后是整个状态管理机制的升级——V2 的状态变量会精确追踪哪些属性被读取，从而实现细粒度的 UI 刷新。

第二，@Local 而不是 @State。V2 中组件内部的局部状态用 @Local 装饰，替换了 V1 的 @State。语义上 @Local 更准确地表达了”这个状态属于组件自己”的含义。

第三，build() 方法依然存在。和 V1 一样，build() 是组件的入口方法，返回组件的 UI 结构。

1.2 @Local：组件的内部状态

@Local 是 V2 中最基本的状态装饰器。它表示”这个状态由组件自己管理，不依赖外部”。

当 this.count 变化时，只有引用了 this.count 的 Text 组件会刷新，Button 不会。这就是 V2 的精确追踪能力。

这在 V1 中是不可能的——V1 的 @State 只要变化，整个组件及其子组件全部重绘。V2 的精确追踪极大减少了不必要的渲染。

1.3 @Param：接收外部传入的状态

自定义组件不可能永远只管理自己的状态。当需要从父组件接收数据时，用 @Param 装饰器。

@Param 的语义很清晰：这个值是从外面传进来的。它等价于 Vue 的 props 或 React 的 props。

这里有个细节值得注意：@Param 必须有初始值。这是因为在 ArkUI 的初始化流程中，属性赋值发生在 build 之前——如果某个 @Param 没有收到传值，它会使用初始值作为默认值。

二、@Builder：自定义构建函数

如果你写过 V1 的 ArkTS，一定对 @Builder 不陌生。但 V2 中的 @Builder 在使用上有一些关键变化。

2.1 为什么需要 @Builder？

考虑一个场景：你有一个 ProfileCard 组件，它在多个地方需要显示用户信息——个人主页、评论列表、搜索建议。但每次显示的样式有细微差异。

如果不做抽象，你会复制粘贴三份相似的代码，然后各改各的。这不仅冗余，而且维护困难。

@Builder 解决了这个问题——它将一段 UI 结构定义为可复用的构建函数。

在 build() 方法中调用 @Builder 方法就像调用普通函数一样，使用 this.方法名() 语法。

与 V1 的一个重要区别：V2 中 @Builder 方法内部可以访问 this 来获取组件的所有状态和 @Param 属性。V1 中 @Builder 是在组件外部单独编译的，需要通过参数传递数据。V2 中 @Builder 和组件共用同一个 this 上下文，使用上更加自然。

3.4 @Builder 与 @BuilderParam 的对比

这两个装饰器名字很像，但定位完全不同：

装饰器 定位 定义位置 调用方式 典型用途
@Builder 构建函数 组件内/全局 this.xxx() / 函数名() UI 代码复用
@BuilderParam 插槽 只能在组件内 this.xxx() 内容自定义/反转型

@Builder 是”组件自己决定 UI”——组件定义好了 UI 结构，其他地方可以复用这段结构。

@BuilderParam 是”外部决定 UI”——组件留出一个空位，外部来决定这个空位里放什么。

这是两种相反的控制流，理解这个区别很重要。

四、@Track：精确追踪

4.1 为什么需要 @Track？

V2 引入了精确追踪机制。默认情况下，装饰器会追踪整个变量的赋值操作。如果一个对象被重新赋值，UI 会刷新；但如果只修改对象的某个属性，默认情况下也会刷新——这是否精确呢？

对于简单类型（number、string、boolean），赋值操作和属性变化是同一回事，没有问题。

但对于对象类型，情况就复杂了：

如果不加任何额外控制，修改 age 会导致引用了 name 的 Text 也刷新。这在小型组件中不是问题，但在复杂组件中会引起级联的、不必要的渲染。

4.2 @Track 的作用

@Track 的作用就是在对象属性的粒度上进行精确追踪：

当 age 变化时，只有第二行 Text 会刷新，第一行不会。@Track 告诉框架：”这个属性是一个独立的追踪单元”。

不是所有的属性都需要 @Track。 需要 @Track 标记的只是那些你希望在属性级别上独立刷新的字段。如果一个属性变化了但你没有 @Track 标记，框架不会在该属性级别做追踪——但它依然会处理对象级别的赋值刷新。

五、@Reusable：组件复用

在列表滚动场景中，频繁的组件创建和销毁会导致性能问题。@Reusable 装饰器允许组件进入复用池而不是被销毁，下次需要时直接从池中取出复用。

5.2 复用 vs 不复用

理解 @Reusable 的核心在于：它不是在优化首次渲染，而是在优化滑动过程中组件的反复创建与销毁。

想象一个列表有 1000 条数据，屏幕上一屏显示 10 条。用户慢慢往下滑——

  • 不用复用：每滑出屏幕一条，组件被销毁；每滑入一条，新建一个组件。销毁→新建→销毁→新建，循环往复。
  • 用复用：滑出屏幕的组件不销毁，而是”洗澡换数据”（aboutToReuse），然后直接放到屏幕另一端显示新数据。

复用减少的是组件的创建和销毁开锁，而不是渲染工作量。在数据量大、组件结构复杂的场景中，效果非常明显。

6.3 生命周期时序

理解组件生命周期的时机很重要：

  1. 组件实例化 — 创建对象，属性赋值
  2. aboutToAppear — 组件即将挂载，准备数据
  3. build() — 渲染 UI
  4. 用户交互 / 状态变化 — 组件更新，build() 重新执行
  5. aboutToDisappear — 组件即将卸载，做清理
  6. 组件销毁 — 释放内存

如果组件还有 @Monitor 监听器，状态变化的回调在 build() 重渲染之前触发。

九、总结

ArkUI V2 的自定义组件体系以 @ComponentV2 为核心，配合 @Builder、@BuilderParam、@Track、@Monitor、@Reusable 等装饰器，构建了一套完整的组件化开发方案。

回顾一下这些装饰器的定位：

装饰器 一句话总结
@ComponentV2 声明这是一个 V2 自定义组件
@Local 组件自己的内部状态
@Param 从父组件接收数据（等价于 props）
@Event 向父组件发送事件（等价于 emit）
@Builder 把一段 UI 变成可复用函数
@BuilderParam 外部决定组件内部的某块内容（插槽）
@Track 精确到属性的刷新追踪
@Monitor 监听状态变化并执行副作用
@Reusable 组件复用优化

组合模式 + 插槽机制 + 精确追踪 = ArkUI V2 组件体系的核心。

在实际项目中，组件化带来的好处是显而易见的：

  • 布局一致性——Card、FormField 这类基础组件统一了页面风格
  • 代码复用率提升——相似的 UI 逻辑不用重复写
  • 可维护性增强——修改一个组件，所有用到的地方都生效
  • 团队协作更高效——组件边界清晰，多人并行开发互不干扰

自定义组件不是银弹，但合理的组件抽象一定是构建复杂应用的关键。
