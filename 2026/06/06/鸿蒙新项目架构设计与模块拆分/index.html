鸿蒙新项目架构设计与模块拆分：从零搭建企业级工程

发表于2026-06-06|更新于2026-06-10|harmonyos
|总字数:4.3k|阅读时长:18分钟|浏览量:

前面有一篇文章讲的是已有项目的架构分层和 MVVM 落地。但有一个更前置的问题被跳过了：一个新项目，第一步该做什么？

不是写代码，是搭结构。

模块怎么分、依赖怎么管、包名怎么起、目录怎么建——这些东西如果在项目一开始没想清楚，等到几十个文件散落在各个目录里的时候，再想重构就晚了。

这篇文章就从零开始，完整走一遍鸿蒙项目从创建到多模块架构搭建的全过程。

    graph TD
    subgraph "本文路线图"
        A[创建新项目] --> B[设计模块结构]
        B --> C[拆分模块]
        C --> D[配置依赖关系]
        D --> E[搭建模块间通信]
        E --> F[填充业务代码]
    end

一、为什么需要模块化？

先看一个反例。假设一个项目没有模块划分，所有代码都塞在 entry 模块里：

这种结构在项目初期跑得很快——文件少、引用直接、不用考虑跨模块问题。

但等到项目到了第二个迭代，问题就来了：

  • 编译慢：改一行代码，整个 entry 重新编译
  • 依赖混乱：工具函数、网络层、业务逻辑全在一个目录，谁也分不清谁依赖谁
  • 没法并行开发：两个人同时改 entry 模块，天天冲突
  • 没法复用：想把网络层抽出来给另一个 App 用？所有代码粘在一起，拆不动

模块化就是把一个大项目拆成若干个小模块，每个模块职责单一、依赖明确、可独立编译。

    graph LR
    subgraph "单体项目"
        A[所有代码] --> B[一坨]
    end
    subgraph "模块化项目"
        C[feature-home] --> D[core]
        E[feature-mine] --> D
        F[feature-login] --> D
        G[common-network] --> D
        H[common-storage] --> D
    end

二、模块拆分策略

模块拆分没有银弹。不同的团队规模、业务复杂度、迭代频率，适合不同的策略。

2.1 按层拆分（Layered）

这是最直观的策略——把代码按技术职责分层：

依赖规则：上层 → 下层，下层不能依赖上层。

    graph TD
    subgraph "UI 层"
        FH[feature-home]
        FM[feature-mine]
        FL[feature-login]
    end
    subgraph "基础设施层"
        CORE[core]
        CN[common-network]
        CS[common-storage]
    end
    subgraph "通用层"
        CUI[common-ui]
        CUTIL[common-utils]
    end

    FH --> CORE
    FH --> CN
    FH --> CUI
    FM --> CORE
    FM --> CN
    FM --> CUI
    FL --> CORE
    FL --> CUI

    CORE --> CUTIL
    CN --> CUTIL
    CS --> CUTIL

适用场景：

  • 项目初期，业务模块不多
  • 团队人数少（3-5 人）
  • 业务边界不清晰，还在探索阶段

优点：结构简单、容易理解、上层模块可以快速替换
缺点：所有业务模块都在同一层，业务耦合风险高

2.2 按功能拆分（Feature-based）

每个业务模块自成一体，包含自己的 View、ViewModel、Model：

核心原则：业务模块之间不能直接依赖。

    graph TD
    subgraph "业务模块"
        FH[feature-home]
        FM[feature-mine]
        FL[feature-login]
        FS[feature-shop]
    end
    subgraph "公共服务"
        CORE[core]
        CN[common-network]
        CS[common-storage]
        ROUTER[router]
    end

    FH --> CORE
    FH --> CN
    FH --> ROUTER
    FM --> CORE
    FM --> ROUTER
    FL --> ROUTER
    FS --> CORE
    FS --> CN
    FS --> ROUTER

    FH -.->|通过 Router 跳转| FM
    FH -.->|通过 Service 接口| FS

适用场景：

  • 业务模块多且独立
  • 多人/多团队并行开发
  • 需要按业务模块独立发布

优点：业务隔离强、并行开发效率高、每个模块可独立测试
缺点：模块间通信成本高、需要路由和接口层

2.3 混合策略（推荐）

实际项目中，纯分层或纯功能拆分都不够用。推荐做法是以功能拆分为主、分层为辅：

    FS --> CORE

    CUI --> CU

2.4 模块粒度控制

模块不是越细越好。一个有用的判断标准：

模块 适合拆分 不适合拆分
网络层 ✅ 独立模块 ❌ 散落在各业务中
存储层 ✅ 独立模块 ❌ 写在 ViewModel 里
登录 ✅ 独立业务模块 ❌ 散落在各页面
详情页 ✅ 独立模块（复杂） ❌（简单）留在业务模块内
工具函数 ✅ common-utils ❌ 每个模块自己写一套
UI 组件 ✅ common-ui ❌ 每个页面重复实现

经验法则：

一个模块应该能在不修改其他模块的前提下独立开发和测试。如果一个模块的变更必然导致其他模块也跟着改，说明拆分位置不对。

四、依赖规则与避免循环依赖

4.1 核心依赖规则

    flowchart TD
    A[业务模块] -->|只能依赖| B[core / common-*]
    B -->|只能依赖| C[common-utils]
    D[entry/壳工程] -->|可以依赖| E[所有模块]
    F[业务模块A] -.->|不能直接依赖| G[业务模块B]
    style C fill:#96f
    style D fill:#f96

三条铁律：

  1. 业务模块 → core/common → common-utils：依赖方向必须从业务层指向基础设施层
  2. 业务模块之间不能直接依赖：如果 A 需要调用 B 的功能，通过路由或 Service 接口
  3. 壳工程（entry）可以依赖所有模块：壳工程负责组装，不负责业务逻辑

4.2 避免循环依赖

循环依赖是模块化中最容易踩的坑。看这个反例：

    flowchart LR
    A[feature-home] -->|依赖| B[core]
    B -->|依赖| C[common-network]
    C -->|反依赖 ❌| A
    style A fill:#f99
    style C fill:#f99

common-network 因为调用了 feature-home 里的某个常量或工具，导致了循环依赖。

解决方案：

  1. 共用代码下沉到 common-utils：如果两个模块都需要某段代码，它不应该属于任何一个业务模块
  2. 接口定义在 core 模块：业务模块提供接口实现，但接口本身定义在 core 或专门的 api 模块中
  3. 使用编译期检查：添加依赖规则检查脚本，在 CI 中阻止循环依赖

九、总结

    mindmap
  新项目架构设计
    模块拆分策略
      按层拆分
      按功能拆分
      混合策略（推荐）
    模块间通信
      路由跳转（HMRouter）
      服务接口（ServiceLocator）
      事件总线（EventBus）
    依赖规则
      业务层 → 基础设施层 → 工具层
      禁止循环依赖
    工程模板
      壳工程（entry）
      业务模块（feature-*）
      核心模块（core）
      通用模块（common-*）

这篇文章从项目创建开始，完整覆盖了鸿蒙多模块工程搭建的各个环节。核心要点：

  1. 模块拆分优先于代码编写——项目开始时花 30 分钟设计模块结构，能为后期节省数倍重构时间
  2. 依赖规则是模块化的生命线——严格执行”业务模块 → core/common → utils”的单向依赖
  3. 接口下沉 + 服务定位器——跨模块通信的通用解，业务模块之间零直接依赖
  4. 壳工程只负责组装——entry 模块的角色是”胶水代码”，不包含任何业务逻辑

下一篇文章我们会在此基础上，深入某个业务模块的具体开发流程，从 ViewModel 设计到 API 联调，完整走一遍 feature 模块的开发过程。
