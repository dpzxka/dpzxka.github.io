鸿蒙 HMRouter 完全解析与二次封装实战：从注解路由到业务封装层

发表于2026-06-02|更新于2026-06-02|harmonyos
|总字数:4.9k|阅读时长:20分钟|浏览量:

鸿蒙的路由方案经历了三个阶段：最初的 router API → 系统的 Navigation 组件 → HMRouter。

router API 因为能力过于基础（不支持生命周期、不支持拦截器、页面间耦合严重）已经被官方放弃。Navigation 组件虽然强大，但使用起来繁琐——每个页面要手动管理 NavPathStack、配置 NavDestination、处理转场动画。对于大型项目来说，这些重复工作严重影响开发效率。

HMRouter 正是在这个背景下出现的。 它对 Navigation 做了系统性封装，通过注解驱动的方式简化路由管理，同时提供了拦截器、生命周期、自定义转场、Dialog 路由等企业级特性。

本文分为两部分：第一部分介绍 HMRouter 的核心概念和基础用法；第二部分实战演示如何对 HMRouter 做二次封装，构建一套类型安全、可维护的业务路由层。

第一部分：HMRouter 基础

一、HMRouter 是什么

1.1 定位

HMRouter 是鸿蒙应用内页面跳转的场景解决方案，底层对系统 Navigation 能力进行了封装。它不是一个全新的路由系统，而是 Navigation 的增强框架。

第二部分：二次封装实战

九、为什么需要二次封装

HMRouter 已经提供了功能完备的基础能力，但在大型项目中，直接使用裸 HMRouterMgr.push({ pageUrl, param }) 会面临几个问题：

问题一：路由地址散落各处。
pageUrl 字符串分散在业务代码中，没有一个统一的管理入口。重构时只能全局搜索替换，容易遗漏。

问题二：参数类型不安全。
param: Record<string, Object> 是开放的类型，编译期无法检查参数是否正确。

问题三：跳转逻辑分散。
如果每个跳转都要判断登录状态、写埋点、处理结果，会形成大量重复代码。

问题四：收口监控困难。
线上出问题时，无法快速定位是谁跳转到哪里的。

二次封装的目标就是解决这些问题。 我们构建一个业务路由层（Business Router Layer），让业务代码的跳转变成类型安全的函数调用。

十四、总结

HMRouter 是目前鸿蒙生态中最成熟的路由框架。它基于 Navigation 但屏蔽了底层复杂性，通过注解驱动的方式提供了拦截器、生命周期、自定义转场、Dialog 路由等企业级特性。

回顾 HMRouter 的核心能力：

而二次封装的核心原则是：框架能力全保留，开发体验加一层。 我们不改动 HMRouter 本身的机制（注解、拦截器、Dialog 都原样使用），只是在 HMRouterMgr.push() 外面包了一层 Navigator.toXxx()，再加上 RoutePath + 类型接口 + 统一拦截器。

封装层本质上是一个防腐层（Anti-Corruption Layer）。未来即使 HMRouter 升级了 API，甚至是切换到了另一个路由框架，只需要修改 Navigator 内部实现，所有业务代码不用动。
