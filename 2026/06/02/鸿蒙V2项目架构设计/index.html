鸿蒙 V2 项目架构设计：从模块划分到 MVVM 分层再到工程落地

发表于2026-06-02|更新于2026-06-02|harmonyos
|总字数:3.4k|阅读时长:15分钟|浏览量:

这个系列写了 9 篇，从 Navigation 到状态管理到 HMRouter，覆盖了 ArkUI V2 开发的方方面面。但有一个问题是读者问得最多的：“在实际项目中，这些东西到底怎么组织在一起？”

单独用某个特性不难，但当你要把这些东西放到一个真实项目中——几十上百个页面、多团队协作、持续迭代——光会用 @Local 和 HMRouterMgr.push() 是不够的。你还需要一套架构约定：代码放哪里、模块怎么分、数据怎么流、路由怎么管。

这篇文章就是我基于前面 9 篇文章的知识体系，整理出来的一套可直接落地的鸿蒙 V2 项目架构方案。它不是一个框架，而是一组经过实践检验的约定和模式。

一、架构总览

1.1 分层原则

整个架构分为四层，每层职责明确：

核心原则：数据向下流，事件向上流。

  • View 层只做 UI 渲染和用户事件转发，不做数据获取
  • ViewModel 层管理状态和业务流程，不直接操作 UI
  • Data 层提供数据，不关心谁在用
  • Route 层处理页面跳转，不关心页面内部逻辑

1.2 数据流向

上图中间的三层箭头清晰地展示了数据流：

  • 红色箭头（向上）：用户操作通过 @Event 从 View 流向 ViewModel
  • 绿色箭头（向下）：ViewModel 通过 Repository 向 Data 层请求数据
  • 蓝色虚线箭头（向上）：数据通过 @Local 自动刷新驱动 View 更新

这和传统的 MVVM 一脉相承，但借助 ArkUI V2 的精确追踪机制，ViewModel 的状态变化会自动驱动 View 刷新——不需要手动调用 setState 或通知观察者。

关键约束：

  1. feature 之间不互相依赖——feature-home 不知道 feature-article 的存在
  2. 所有 feature 依赖 common 和 shared——共享 UI、工具、数据模型

四、ViewModel 层：状态管理

4.1 模式选择

在 ArkUI V2 中，ViewModel 层不是一个单独的类——它就是 @ComponentV2 组件中的状态装饰器。因为 ArkUI 的 UI 本身就是状态驱动的，不需要像 Flutter 那样用 ChangeNotifier 或者 React 那样用 useState 之外的独立状态管理库。

4.4 ViewModel 的边界

我划了几个原则来保持 ViewModel 的整洁：

原则一：ViewModel 不做 UI 操作。 不直接操作 Animation、不设置组件属性、不访问 DOM。

原则二：ViewModel 不做网络请求。 网络请求在 Data 层的 Repository 中完成。

原则三：一个 Page 对应一个 ViewModel 范围。 不要把全局状态塞进一个 Page 的 ViewModel。

十、状态装饰器选型决策树

架构定了、模块分了、代码写起来了——但开发中每天都会遇到的问题：”这个状态到底该用哪个装饰器？”

下面这张决策树可以帮助你和团队快速决策：

使用路径：

  • 状态只属于组件自己 → @Local
  • 状态从外部传入，只是展示 → @Param
  • 状态从外部传入，需要通知父组件修改 → @Param + @Event
  • 状态需要跨多层传递 → @Provider/@Consumer
  • 状态需要在全局使用 → AppStorage

十一、总结

回顾整篇文章，核心就三句话：

数据流向决定架构。 数据从 Data 层流向 ViewModel 层再流向 View 层，事件反向流动——理解了这个流向，模块划分和代码组织就有了依据。

模块边界决定可维护性。 feature 之间不互相依赖，router 独立于业务，common 提供基础能力——每个模块的边界清晰了，团队协作才不会踩脚。

约定大于配置。 View 层不直接调 API，ViewModel 不做 UI 操作，组件的 @Param + @Event 模式——这些约定不需要框架支持，只需要团队遵守，就能保证项目在半年后仍然可维护。

这套架构方案不是凭空想出来的，而是从前面 9 篇文章的知识点中提炼出来的实战模式。如果你从第一篇读到这一篇，现在应该已经具备独立搭建一个鸿蒙 V2 大型项目的能力了。

欢迎在实践中发现问题或者有更好的方案，随时交流。
