一、为什么需要 FrameNode

声明式UI（@Component + build()）是ArkUI的主流开发方式，但它有一个天然限制：组件树结构一旦声明，只能通过状态驱动整体重渲染，无法局部调整节点关系。

举个例子：你想把一棵子树从父节点A移到父节点B——用声明式写法，你只能通过条件渲染销毁A、重建B，整个子树会丢失状态。而用FrameNode，你可以直接操作节点树，把子节点”拔出来”插到另一个位置，只触发局部渲染。

官方定义（FrameNode API参考）：

FrameNode表示组件树的实体节点，支持节点树操作、自定义绘制与布局、位置查询、动画等能力。

适用场景：

  • 动态增删组件树节点（如拖拽排序、动态面板）
  • 子树在不同父节点间移动（如画布元素拖拽）
  • 需要精确控制渲染刷新范围
  • BuilderNode预创建组件树，按需挂载

约束条件（来自官方文档）：

  • 本模块首批接口从 API version 11 开始支持
  • 当前不支持在预览器中使用FrameNode节点
  • FrameNode节点暂不支持拖拽
  • FrameNode对象不支持JSON序列化

十、常见问题

Q1：FrameNode和@Component有什么区别？

@Component 是声明式UI，通过状态驱动重渲染；FrameNode是命令式API，直接操作节点树。声明式UI开发效率高，但节点结构灵活度低；FrameNode灵活度高，但代码量大。推荐先用声明式UI，遇到声明式无法满足的需求再用FrameNode。

Q2：什么时候用BuilderNode，什么时候用typeNode？

BuilderNode通过@Builder函数生成完整的组件树（含子组件和样式），适合复杂组件组合；typeNode只创建空节点，适合简单的占位或结构搭建。如果需要系统组件（Button/Text/Image等），用BuilderNode；如果只需要容器节点，用typeNode更轻量。

Q3：FrameNode节点怎么触发重绘？

修改FrameNode的属性后，系统会自动标记需要重绘。如果需要手动触发，可以调用 markNeedRender() 方法。对于BuilderNode，修改@Builder参数后需要重新 build() 或通过状态更新触发。

Q4：NodeContainer和ContentSlot有什么区别？

NodeContainer 接收一个 NodeController，由Controller的 makeNode() 返回FrameNode根节点；ContentSlot 接收一个 NodeContent，通过 addFrameNode() 动态添加节点。两者都是将动态节点嵌入声明式组件树的方式，NodeContainer适合有完整控制器逻辑的场景，ContentSlot适合轻量级的动态插入。
